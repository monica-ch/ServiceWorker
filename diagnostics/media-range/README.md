# Media Range observations for ServiceWorker #1201

This is a **diagnostic/interoperability probe**, not a normative WPT and not a
test of an agreed resource-continuity contract. It prepares discussion of
[w3c/ServiceWorker#1201](https://github.com/w3c/ServiceWorker/issues/1201).
The specification is unchanged. Do not delay TPAC to obtain a passing test:
the exact expected behavior for responses from changing resources needs
agreement first.

## Run

Requires Python 3. No packages, external media assets, certificates, browser
flags or internet access are needed.

From the repository root:

```powershell
python diagnostics\media-range\server.py
```

Open the printed URL in a **fresh, disposable browser profile** and choose
**Run observations**. `?autorun` starts automatically. Do not use `file:` or
disable browser security. The page refuses to proceed if it finds an existing
service worker rather than deleting registrations belonging to another test.
It unregisters only its own registration at completion.

The server binds two ephemeral/local ports on `127.0.0.1`: a page origin and
a second media origin. The default page port is 8765; `--port 0` selects a
free port. A port difference makes the media cross-origin, but not cross-site.
Loopback is a trustworthy context for service workers.

Close the disposable profile and stop the server with Ctrl+C when finished.
Use **Download JSON** to save the observations. For automation,
`window.__tpacResult.complete === true` signals that collection has finished,
not that a conformance requirement passed. Inspect `errors` and every case's
`diagnostics` before interpreting the result.

## What this measures

For each of same-origin, cross-origin no-CORS and cross-origin CORS audio:

1. An uncontrolled client provides a baseline.
2. A controlled client records fetch events but uses network fallback (no
   `respondWith`).
3. A controlled client uses `respondWith(fetch(event.request))`, without
   reconstructing or modifying the original Request.

Each case loads metadata and seeks to 75% of a stable 120-second PCM WAV.
**Script never adds a Range header.** Any Range header at the media server
was generated by the browser's media/network loading path.

Two independent observation points record:

- Service worker: `FetchEvent.request.headers.get("Range")`, request mode,
  destination, URL, client ID and, for pass-through, response type/status.
- Media server: received Range header, response status, byte offsets and
  transport completion. Opaque response status is 0 in the worker; the server
  is the independent source of the actual HTTP status.

Records are correlated by a unique run ID and case-specific media URL.
Repeated requests retain the same URL within a case. Compare the raw records;
one fetch event is not proof that every subsequent Range was intercepted.
The summary does not turn absent events into a PASS or FAIL:

| Observation | Interpretation |
| --- | --- |
| Network Range and matching fetch-event record | Interception and header exposure observed for those requests |
| Network Range but no fetch event in a controlled case | No interception observed within the collection window; investigate bypass versus missing instrumentation |
| Fetch event with Range `null` | An event occurred but that request did not expose Range |
| No network Range | Inconclusive for Range interception; the UA may use a full response or already-buffered media |
| Setup, media or recording error | Invalid/incomplete measurement; inspect diagnostics |

Compare network Range values for pass-through with fetch-event Range values.
This probes preservation of the original request, but does not test every
request-cloning or header-mutation rule. Network fallback is a useful control
for whether adding an inner fetch changes the observed behavior.

## Bounds and limitations

- The WAV is generated from a 44-byte header plus zero-filled PCM, about
  10.6 MB logically. It is **not** allocated or downloaded as a binary fixture.
  Responses stream in 16 KiB chunks, paced at roughly 800 KiB/s; the client
  normally aborts when each case ends.
- Metadata observation is bounded to 8 seconds; seek observation to 1.5
  seconds. A seek does not guarantee another network request. No playback or
  autoplay permission is required.
- The resource and ETag never change. There is no version-switch test,
  integrity test, cache-continuity verdict or fake partial response.
- The server implements single byte ranges, valid 200/206 responses and
  unsatisfiable-range 416 responses. A 416 server unit test is **not** a test
  of opaque-response Fetch security behavior.
- Collection is limited to 32 runs and 1000 events per run; exceeding limits
  produces an explicit error. Restart the server to clear recorded runs.
- The final snapshot is finite. Transport completions can arrive after it;
  recorded bytes are bytes written by the server, not proof of client receipt.
- The worker records observations using a same-origin POST. This is
  instrumentation and can affect timing. Recording failures are surfaced.
- Results depend on browser version, platform, WAV support and media-loading
  policy. A two-port localhost test is not a cross-site or public-HTTPS test.
  Run in Gecko and WebKit as well as Blink before claiming interoperation.

## Existing WPT evidence and next steps

### Local preparation measurements

Two nine-case runs each in headless Windows Edge 155.0.4283.45 and Chromium
151.0.7922.34 recorded initial `bytes=0-` and seek-generated `bytes=7929856-`
requests in every case. All controlled cases exposed both values through
`FetchEvent.request`. Pass-through server records retained those same Range
values. Uncontrolled baselines produced no worker records. No setup, media
or recording diagnostics were reported.

These are stable-resource observations, **not** a conformance expectation
encoded in this probe. Both products share Blink; no local Gecko/WebKit result
is claimed. Different browsers may make different requests. Neither a
particular byte offset nor a particular request count is required.

### Prior art and discussion

Prior art (not copied or replaced here):

- [UA media Range and pass-through tests](https://wpt.fyi/results/fetch/range/sw.https.window.html)
- [Range service worker source](https://github.com/web-platform-tests/wpt/blob/master/fetch/range/resources/range-sw.js)
- [Author-created Range interception](https://wpt.fyi/results/fetch/range/sw-intercept-range.https.window.html)
- [Opaque 416 behavior](https://wpt.fyi/results/fetch/range/sw-416.https.window.html)
- [HTML media response verification](https://html.spec.whatwg.org/multipage/media.html#verify-a-media-response)

These cover pieces of Range/Fetch behavior, not the exact contract for
changing the resource between partial responses through a service worker.
This repository holds the Service Worker specification, not the WPT harness;
the probe deliberately does not use `testharness.js` to turn a collection
of incompatible outcomes into passing conformance tests.

Ask vendors at TPAC:

> When a UA generates subsequent range requests for media, should they continue
> through the service worker when the UA cannot verify that the responses
> belong to the same underlying resource?

Discuss whether continuity is the worker's responsibility, the UA should
verify and fail/restart, the UA may/must bypass the worker, or a different
HTML/Fetch mechanism is needed. Agree expected behavior and specification
ownership across HTML, Fetch and Service Worker.

After agreement, add focused WPTs for UA Range exposure, pass-through Range
preservation, changed-resource responses, and the selected outcome when
continuity cannot be established. Keep opaque 206/416 security coverage
separate. Do not assert a currently unagreed continuity outcome.

## Server checks

From the repository root:

```powershell
python -m unittest discover -s diagnostics\media-range -p test_server.py -v
```

These check the synthetic WAV, exact range parsing, 206/416 framing, CORS,
observation recording and explicit error handling. They do not substitute
for running the browser diagnostic.
